## 0.5 — Merchant normalisation quality — **GATE for Phase 3**

### Sample
Dorcas (`c6b1dd54-0c90-47ab-b098-d724d27471f7`) on CFO Staging:
- 233 total non-deleted transactions
- 89 distinct `description` values
- 89 distinct `raw_description` values (1:1 with description)
- Window: 2026-02-01 to 2026-04-30 (3 months)
- Avg 2.6 transactions per description

### Per-description fragmentation test (description maps to multiple raw_descriptions)
**Result: 0 rows.** Every `description` maps to exactly one `raw_description`. They are 1:1 — `description` is effectively a copy of `raw_description` with no merging performed by the ingest pipeline.

### Key-collapse test (descriptions that should have merged under a normalised key)
**Result: 0 rows.** No two descriptions collapse to the same alphanumeric-only key. There's no obvious "same merchant, different punctuation" fragmentation visible at this granularity.

### Top descriptions sample (the real story)
| description | tx count | raw_description |
|---|---:|---|
| `POS PURCHASE POLLO TROPICAL #142` | 13 | `POS PURCHASE POLLO TROPICAL #142` |
| `POS PURCHASE MCDONALDS #2218` | 9 | (same) |
| `POS PURCHASE POLLO TROPICAL DRIVE THRU` | 9 | (same) |
| `POS PURCHASE TOTAL 0451 CAROLINA PR` | 8 | (same) |
| `ATM WITHDRAWAL FIRSTBANK CAROLINA 003` | 7 | (same) |
| `POS PURCHASE WALGREENS #6841` | 7 | (same) |
| `POS PURCHASE EL MESON SANDWICHES` | 7 | (same) |
| `POS PURCHASE TOTAL 1109 BAYAMON PR` | 4 | (same) |

### Interpretation
Descriptions carry the bank prefix (`POS PURCHASE`, `ATM WITHDRAWAL`, `DIRECT DEP`), branch numbers (`#142`, `#2218`), and locations (`CAROLINA PR`, `BAYAMON PR`). The two `POLLO TROPICAL` entries (`#142` and `DRIVE THRU`) and the two `TOTAL` entries (`0451 CAROLINA` and `1109 BAYAMON`) are clearly the same brand/chain but appear as separate descriptions.

The mechanical normalisation test missed this because the strings genuinely differ — branch suffixes, drive-thru markers, location codes. A proper merchant normaliser would need to:
1. Strip prefixes (`POS PURCHASE`, `ATM WITHDRAWAL`, `DIRECT DEP`)
2. Strip branch codes (`#NNNN`, ` NNNN`)
3. Strip location suffixes (`CAROLINA PR`, `BAYAMON PR`)
4. Strip channel markers (`DRIVE THRU`)
5. Collapse whitespace

### Decision: **Path A** (with caveats)

**Use `description` as the merchant key for `merchant_aggregates`. No schema change in Session A.**

Rationale:
1. Each fragmented description (e.g. `POLLO TROPICAL #142` with 13 tx) is still a meaningful behavioural cluster — recurrence, trend, and time-pattern features will be sensible.
2. A proper SQL-based normaliser is non-trivial and would expand Session A scope significantly. Branch-code stripping varies by bank.
3. The product can still demonstrate the layered architecture's value with branch-level merchants. Brand-level rollup is a follow-up enhancement.
4. The existing `normaliseMerchant()` helper in [pattern-detectors.ts:9](cfos-office/src/lib/analytics/pattern-detectors.ts:9) can be promoted into a proper normaliser in a future session — it already handles some of these cases for the Layer 3 detector library.

### Follow-up flagged for Lewis
> **Brand-level merchant normalisation is needed for the CFO to recognise chains.** Today `POLLO TROPICAL #142` and `POLLO TROPICAL DRIVE THRU` are treated as separate merchants. The cluster-behaviour engine works fine at the description level for foundational features, but brand-level rollup will be needed for higher-quality CFO commentary. Recommended approach: in a future session, add a `merchant_normalised TEXT` column on `transactions` with a backfill function that strips bank prefixes, branch codes, and location suffixes. Reuse and extend [`normaliseMerchant()` in pattern-detectors.ts:9](cfos-office/src/lib/analytics/pattern-detectors.ts:9).

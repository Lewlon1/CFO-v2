# v2.2 Chat Intelligence — onboarding output comparison (before/after)

**Date:** 2026-05-16
**Branch:** `feature/v2.2-chat-intelligence` (Session 26 — Dialogue-as-Moat)
**Author:** Claude (audit pass)
**Inputs:** branch HEAD vs `main`; live `run-personas-v2.ts --prompt-version v1|v2` against CFO Staging (`qlbhvlssksnrhsleadzn`); judged `compare-first-insight.ts` against User Lew 1.

## 0. Headline

The branch reworks the **post-CSV intelligence layer** behind a cohort feature flag (`isChatIntelligenceV2Enabled`, true for `beta_cohort ∈ {wave_1, wave_1_5}` or `CHAT_INTELLIGENCE_V2_FORCE=1`). v1 codepaths are intact; v2 lives alongside. Rollback is a flag flip, not a revert.

Of the five user-visible surfaces touched by the branch:

| # | Surface | Magnitude | What a user sees |
|---|---|---|---|
| 1 | Value Map flow | Small (under the hood) | Same 10 cards, same flow, same archetype. Underneath: intent cards stop polluting `value_category_rules`; `unsure` replaces `no_idea` in copy and DB writes; the Gap analyser stops substring-matching broken merchant rules. |
| 2 | Archetype reveal | None visible | Pure enum rename surface; archetype JSON shape unchanged. |
| 3 | First-insight chat | **Large** | v1 wrote a brief in 4 acts driven by a precomputed `InsightPayload`. v2 holds a hypothesis, calls 1–3 tools, writes one specific observation, ends with an invitation. Different prose, different structure, different conversation chips. Post-LLM validators silently correct citations / projections / voice / chips. |
| 4 | The Gap page | **Large** | v1 rendered a single belief/reality narrative card per category, with one of five `gap_type` variants underneath. v2 renders three distinct card shapes (`SingleIntent` / `MultiIntent` / `Coverage`) topped by a `ValueMapSummary` header that surfaces classifications count + coverage % + staleness. |
| 5 | LabelTransactionsBlock | **Net new** | An inline chat primitive that didn't exist on v1: per-transaction quadrant pills with a "Send to C." gate, an 800ms "C. is reading…" beat, a read-only completed state. The chat surface can now ask the user to label 3-6 transactions without leaving the conversation. |

Two cross-cutting concerns sit alongside the surfaces:

- **Output-discipline validators** run after every v2 first-insight LLM message — citations against an allowlist, projections against `propose_experiment` outputs, banned phrases, chip nouns. Bad numbers / projections / voice get an italic server correction appended to the message body. Bad chips are stripped; empty `[OPTIONS]` blocks are dropped entirely. Both fire `user_events` for telemetry.
- **Telemetry surfaces** — a new `proposed_experiments` table (migration 051) captures every `propose_experiment` tool call. `user_events` gains `first_insight_validator_fired` and `first_insight_chips_stripped`.

The rest of this document walks each surface in detail, then attaches the live runtime comparison.

## 1. Surface 1: Value Map flow

### v1 state (on `main`)

- `ValueMapTransaction` has no `category_id` or `granularity` ([git show main:cfos-office/src/lib/value-map/types.ts](cfos-office/src/lib/value-map/types.ts)).
- `link-session` writes one `value_category_rules` row per decided card, hardcoded to `match_type: 'merchant'` with `match_value = r.merchant.toLowerCase()` ([git show main:cfos-office/src/app/api/value-map/link-session/route.ts:108-130](cfos-office/src/app/api/value-map/link-session/route.ts)).

SESSION-LOG: "the prior implementation wrote `match_type: 'merchant'` with `match_value` = sample card label, which the Gap analyser then tried to substring-match against bank transaction descriptions and never found anything."

### v2 state (on branch)

- `ValueMapTransaction` extended with `category_id?: string | null` + `granularity?: 'category' | 'intent'` ([cfos-office/src/lib/value-map/types.ts:7-25](cfos-office/src/lib/value-map/types.ts:7)).
- All 10 `SAMPLE_TRANSACTIONS` carry explicit mappings ([cfos-office/src/lib/value-map/constants.ts:106](cfos-office/src/lib/value-map/constants.ts:106)): e.g. `vm-rent → housing/category`, `vm-takeaway → eat_drinking_out/intent`, `vm-utility → utilities_bills/category`.

Intent cards write only to `value_map_results`. Their quadrant choice is preserved for the v2 multi-intent Gap rendering to read directly.
- Real-transaction flows (personal / check-in) still write merchant rules, now tagged `source: 'value_map_personal'` so future sample-card cleanups don't sweep them up ([cfos-office/src/components/value-map/value-map-flow.tsx](cfos-office/src/components/value-map/value-map-flow.tsx)).
- `no_idea` → `unsure` rename across 25 files / 53 refs. Generated `supabase/types.ts` preserves both DB enum values; only the `no_idea` enum value in `value_category_type` is retained (deprecation, not drop — drop comes in a follow-up cleanup migration). Hand-written types switch to `'unsure'`.
- Migration 050 deletes 277 broken VM merchant rules from staging; drops a redundant 3-col unique constraint on `value_category_rules`.

### Why it changed

SESSION-LOG verdict: "Sample-card flow is now correct. Going forward, completing the Value Map seeds only category-precise rules. Intent cards … write to `value_map_results` for the V2 multi-intent path to read, but no longer pollute `value_category_rules`. User Lew 1's broken-rule count is 0; was 9."

### What a user sees

Nothing visually changes during the Value Map flow itself. Same 10 cards, same order, same archetype reveal. The "I have no idea" affordance changes to "Unsure" copy. Everything else lands downstream: a clean `value_category_rules` table that lets the Gap analyser actually match, and a `value_map_results` table populated with intent-level quadrant choices that the v2 multi-intent Gap page can read directly.

### Risk / fallback

Low risk. The DB enum keeps both `unsure` and `no_idea` values, so any straggler v1 writes still validate. The merchant-rule write path is unchanged for real-transaction flows (only sample-card flows changed). Migration 050 is destructive on staging only; production stays on the v1 broken state until Lewis runs it manually.

## 3. Surface 3: First-insight chat (the big change)

### v1 state — narrate a precomputed payload

`buildFirstInsightContext(payload: InsightPayload, ...)` at [cfos-office/src/lib/ai/context-builder.ts:186](cfos-office/src/lib/ai/context-builder.ts:186) writes a strict template. The shape:

- A **QUOTABLE FACTS allowlist** — the only numbers and merchants the LLM is permitted to cite. Sourced from `computeFirstInsight()` ([cfos-office/src/lib/analytics/insight-engine.ts](cfos-office/src/lib/analytics/insight-engine.ts) — `buildSuggestedResponses` etc.). Every figure ≥ 10 must appear verbatim or be rephrased qualitatively.
- A **patterns-to-narrate list** in fixed order: `headline → gap → numbers → hidden_pattern → action → hook`. The LLM walks each pattern's `narrative_prompt` and renders prose.
- Optional **EXPERIMENT** block with monthly/annual savings bands the LLM must quote verbatim.
- **STAT CARDS** block emitted as `[STATS]...[/STATS]`.
- **HOOK** prompt + **SUGGESTED RESPONSES** with exactly three chips emitted as `[OPTIONS]...[/OPTIONS]`.
- A **NOT AVAILABLE** sentinel block forbidding references to income, savings rate, surplus, age, etc.

Tool surface: only the existing chat toolbox; in practice the v1 first-insight is narrated from the precomputed payload alone (the live run confirmed zero tool calls).

### v2 state — hold a hypothesis, call 1-3 tools, write one thing

`buildFirstInsightContextV2(supabase, userId, profile, archetype, ...)` at [cfos-office/src/lib/ai/context-builder.ts:429](cfos-office/src/lib/ai/context-builder.ts:429) returns an 8-section async prompt joined with `\n\n---\n\n`:

1. **The user** — brief: display name, country/currency, goal (own words), entry struggle, monthly income (if known), monthly rent (if known) ([lines 459-473](cfos-office/src/lib/ai/context-builder.ts:459))
2. **Value Map** — archetype, baseline-taken-at + staleness, classifications per quadrant (Foundation / Investment / Leak / Burden / Unsure) with explicit "treat as hypothesis, not ground truth" framing ([lines 475-501](cfos-office/src/lib/ai/context-builder.ts:475))
3. **Data available** — n_transactions + n_months + date range ([lines 503-506](cfos-office/src/lib/ai/context-builder.ts:503))
4. **Memory surface** — top 30 confirmed merchant labels from `value_category_rules` filtered to `source IN ('correction', 'learned')`. Crucially excludes `source = 'value_map'` so seed rules don't pose as user-confirmed corrections ([lines 508-531](cfos-office/src/lib/ai/context-builder.ts:508), with rationale in the function-header comment at [lines 423-427](cfos-office/src/lib/ai/context-builder.ts:423))
5. **How to approach the first message** — explicit four-step recipe: form a hypothesis, call 1-3 detective tools, write ONE specific observation, end with a question / action / labelling invitation ([lines 533-555](cfos-office/src/lib/ai/context-builder.ts:533))
6. **Voice rules** — first-person C., specific merchants/amounts/dates, 100-180 word body cap, signoff on its own line, no compute-in-prose, no `I noticed`, no `advice`/`advise`, no product name ([lines 557-574](cfos-office/src/lib/ai/context-builder.ts:557))
7. **Chips** — 2-4 chips, each referencing a specific noun, advancing the dialogue, never navigational or generic. Three shapes: labelling / action / specificity. Empty `[OPTIONS]` better than fake chips ([lines 576-594](cfos-office/src/lib/ai/context-builder.ts:576))
8. **Surface learning** — when a conversation changes what the system knows, name what changed and what it unlocks. Specific, quantified ([lines 596-609](cfos-office/src/lib/ai/context-builder.ts:596))

Plus a brand-new tool surface ([cfos-office/src/lib/ai/tools/](cfos-office/src/lib/ai/tools/)):

- **Reading** — `get_transactions`, `get_top_merchants`
- **Detective** — `find_money_clusters`, `find_temporal_signals`, `find_trend_changes`, `find_outliers`, `find_value_gaps`
- **Action** — `propose_experiment` (writes telemetry row to `proposed_experiments`)
- **Labelling** — `label_transactions` (returns `render_directive` for in-chat UI)

All tools return story-shaped data with a `data_confidence` field ('high' | 'medium' | 'low' | null with reason).

### What a user sees — concrete diff

The live `compare-first-insight.ts --judge` run against User Lew 1 (`bcfbb511-9b0e-4c13-b566-1ef5b0829fa0`, 191 transactions, 4 months, Value Map = "The Quiet Fortress") on 2026-05-16 produced the deltas captured in [Appendix A](#appendix-a-companion-file). Headlines:

| Dimension | v1 | v2 |
|---|---|---|
| Body length | 1456 chars (~270 words) | 1084 chars (~225 words) |
| Tool calls | 0 | 4 (`find_money_clusters` etc.) |
| Merchants named in narrative | 0 (only categories: "travel", "streaming") | 6 (Flaherty's Irish Pub, Bar Schuss, El Corte Inglés, Aldi, Ryanair, EasyJet) |
| Numbers cited | only those in QUOTABLE FACTS payload | live merchant amounts pulled via tools (€30.60, €30, €24.90, €71, €855, ~€60/month) |
| Goal-relevance framing | aggregate (38% travel vs €15k debt) | specific (weekend pub spend, redirect ~€60/month toward debt) |
| Hook style | broad ("Show me every active subscription" / "Break down my travel" / "Let's get started") | narrative-derived ("Dig into the weekend pub spend" / "Talk through the €855 in flights" / "Show full Feb breakdown") |
| Judge specificity (L1) | **2/5** | **5/5** |
| Judge conversion likelihood (L6) | **3/5** | **4/5** |
| Judge hard-rule pass | **fail (H1: no merchant named)** | **fail (H6: 225 words exceeds 180-word limit)** |

Side-by-side response excerpts (full text in Appendix A):

**v1 response:**
> Travel is carrying a disproportionate weight in your spending. At 38% of total outgoings — €861 in the most recent month — it's the single category most at odds with a goal built around clearing €15,000 of debt… Under the surface, there are 22 recurring bills totalling €758 a month… One specific overlap: streaming. You're paying for duplicate subscriptions, and the cheapest duplicate is running roughly €7 a month, around €80 a year. Ten minutes to cancel. Want a draft of the cancellation steps?

**v2 response:**
> Your leak-tagged spend in February came to **€123.71** — about 11% of what you spent that month. The biggest chunks: Flaherty's Irish Pub (€30.60), Bar Schuss (€30), and El Corte Inglés (€24.90). That eating and drinking-out spend is entirely concentrated on **weekend evenings**… You've classified solo takeaways as Foundation and dinners with friends as Investment. These look like neither — they're pub visits, which puts them in ambiguous territory… If you redirected even half of the monthly Leak spend toward debt clearance, that's roughly **€60/month** back on your goal.

### Why it changed

SESSION-LOG, "Architectural principles": (1) tools return story-shaped data, not pattern enumerations; (2) the system holds hypotheses, not claims; (3) the CFO learns through dialogue, not pre-classification; (4) conversations make the system better and users feel it; (5) LLM interprets, system computes.

The v1 architecture optimised for *safety* (no hallucinated numbers, no merchant invention) at the cost of *specificity* (the LLM couldn't surface a single real merchant because the QUOTABLE FACTS list rarely contained one). v2 trades narrow-allowlist safety for **tool-grounded specificity** — the LLM pulls fresh numbers/merchants via tools and the validators (Surface 6) check them against the tool outputs after the fact.

### Risk / fallback

Two real risks, both surfaced by the live run:

- **Length discipline.** v2's prompt instructs 100-180 words for the body, but the live run came in at 225 words and the judge failed H6 (length). The body length is enforced by the prompt only, not the validator — a long response still ships. If 5%+ of conversations exceed 180 words, the v2 voice loses its tight register. **Watch this in telemetry.**
- **Tool reliance.** v2 depends on the 10 new tools returning story-shaped data with non-null `data_confidence`. If any tool starts returning `data_confidence: 'low'` for most users (e.g. because of a data gap), the LLM has nothing concrete to cite and falls back to vague prose. The validators will then fire `first_insight_validator_fired` on every conversation. **Watch the validator-fired rate; target < 5% per the rollout doc.**

Rollback is `UPDATE user_profiles SET beta_cohort = NULL WHERE id = '<user>'` (or remove the env var). v1 path is intact and ships immediately.

## 4. Surface 4: The Gap page

### v1 state — single narrative card, five gap_type variants

The v1 page at [cfos-office/src/app/(office)/office/values/the-gap/page.tsx](cfos-office/src/app/(office)/office/values/the-gap/page.tsx) calls `analyseGap(supabase, user.id, 3)` and maps each `CategoryGap` into a `{ trait_key, trait_value: { belief, reality, status }, confidence }` shape rendered by `TheGapClient`.

The five `gap_type` variants ([git show main:cfos-office/src/lib/analytics/gap-analyser.ts](cfos-office/src/lib/analytics/gap-analyser.ts)):
- `aligned` — Value Map matches actual
- `over_investing` — user said Investment, actual spend is higher than expected
- `leaking_despite_awareness` — user said Leak and is still leaking
- `hidden_burden` — user said Foundation/Investment, actual reads as Burden
- `undervalued` — user said the category matters less than the spend implies

Mapped to four display statuses (`aligned | gap | eliminated | partial`) inside `mapGapStatus()` ([page.tsx:7-15](cfos-office/src/app/(office)/office/values/the-gap/page.tsx:7)).

Source of stated values: `value_category_rules` (the rules table that the v1 `link-session` polluted with merchant rows). The Gap analyser substring-matches the rule's `match_value` against bank descriptions — which is why the 277 broken merchant rules existed and why the v1 Gap page tended to show fewer matches than expected.

### v2 state — three shapes + ValueMapSummary header

The v2 page renders [TheGapV2Client.tsx](cfos-office/src/app/(office)/office/values/the-gap/TheGapV2Client.tsx) (gated behind the cohort flag on the page server-component). It receives:

- `gaps: GapV2[]` — discriminated union of three shapes
- `metadata: ValueMapMetadata` — `staleness_days`, `classifications_count`, `coverage_pct`
- `vmRowsByQuadrant: VmRowsByQuadrant` — for the new summary header
- `currency`, `transactionCount`, `hasValueMap`

The three card shapes:

1. **[SingleIntentGapCard](cfos-office/src/app/(office)/office/values/the-gap/components/SingleIntentGapCard.tsx)** — "one stated value, aligned reality". All Value Map cards in the category share a single quadrant; actual monthly spend is homogeneous. Renders category name, monthly spend, % of total, quadrant pip + label, italic serif `narrative_hint`.
2. **[MultiIntentGapCard](cfos-office/src/app/(office)/office/values/the-gap/components/MultiIntentGapCard.tsx)** — "one stated value, fragmented reality". Category has multiple stated quadrants OR mixed granularities. Spend is time-sliced and shown per-quadrant with per-quadrant merchant lists. Optional `after_labelling` state (server threshold deferred). Primary CTAs: "walk through" / "talk leak".
3. **[CoverageGapCard](cfos-office/src/app/(office)/office/values/the-gap/components/CoverageGapCard.tsx)** — "no stated value, active spend". Spend in a category but no Value Map card for it. Dashed border distinguishes from stated-intent cards. Secondary CTA: "Tell C.".

Plus a brand-new **[ValueMapSummary](cfos-office/src/app/(office)/office/values/the-gap/components/ValueMapSummary.tsx)** header block that surfaces `staleness_days` + `classifications_count` + `coverage_pct` so the user understands how fresh and broad their stated-values baseline is before reading the cards.

Source of stated values: `value_map_results` directly (joined to `SAMPLE_TRANSACTIONS` for `category_id` + `granularity`). The merchant-rule substring matching layer is gone.

Dispatch logic ([cfos-office/src/lib/analytics/gap-analyser.ts:703](cfos-office/src/lib/analytics/gap-analyser.ts:703)):
- `single_intent` — all non-unsure rules in category map to same quadrant + uniform granularity
- `multi_intent` — multiple distinct quadrants OR mixed (category + intent) granularities
- `coverage_gap` — spend in category exists, monthly ≥ €10 equivalent, but zero Value Map cards

### What a user sees — concrete diff

| Layout element | v1 | v2 |
|---|---|---|
| Header | (none beyond page title) | `ValueMapSummary`: "Foundation 4 cards · Investment 3 · Leak 2 · Unsure 1 · taken 4 days ago" |
| Card shape | Single belief/reality narrative card per `CategoryGap`, status pip (aligned/gap/eliminated/partial) | Three distinct cards depending on shape — different visual structure each |
| Stated-value source | `value_category_rules` (substring-matched against bank descriptions) | `value_map_results` (direct join to sample-card `category_id`) |
| Multi-intent case | Hidden — a single category with takeaway-as-Foundation + dinners-as-Investment collapses to one belief/reality row | First-class — `MultiIntentGapCard` shows both intents side-by-side with per-quadrant merchant slices |
| No-stated-value case | Hidden — the analyser only surfaces categories the user *did* classify | First-class — `CoverageGapCard` with dashed border and "Tell C." CTA |
| Empty state | One-line copy | Conditional copy distinguishing "no VM", "no transactions", "both", "all-aligned" |

### Risk / fallback

Low risk. The v1 page lives at the same URL behind the cohort flag (the page server-component checks `isChatIntelligenceV2Enabled` and routes to `TheGapClient` or `TheGapV2Client`). For non-cohort users nothing changes.

One thing to watch: the `after_labelling` state on `MultiIntentGapCard` is wired in the UI but defaults to `initial` — the server-side derivation ("3+ confirmed merchants covering 70%+ of category") is deferred per SESSION-LOG. The `initial` rendering looks complete enough to ship but the "labelled" state never fires until the threshold computation lands.

## 5. Surface 5: LabelTransactionsBlock

### v1 state

Did not exist.

### v2 state — inline labelling primitive in chat

[cfos-office/src/components/chat/LabelTransactionsBlock.tsx](cfos-office/src/components/chat/LabelTransactionsBlock.tsx) (505 lines). Triggered when the LLM calls the `label_transactions` tool ([cfos-office/src/lib/ai/tools/label-transactions.ts](cfos-office/src/lib/ai/tools/label-transactions.ts)); the tool returns a `render_directive` payload with `directiveId`, `question`, optional `contextHint`, `transactions` (3-6 items with id/date/merchant/amount/category), and exactly 5 `options` (Foundation / Investment / Leak / Burden / Unsure with hex colours from the tool, NOT the LLM).

[MessageList.tsx](cfos-office/src/components/chat/MessageList.tsx) detects the directive in the assistant message and renders the block inline. Behaviour:

- 5 quadrant pills per transaction (Foundation / Investment / Leak / Burden / Unsure)
- "Send to C." button **disabled until every transaction is labelled**
- On submit: each label POSTs to `/api/corrections/signal` (existing endpoint, no changes)
- 800ms "C. is reading…" beat ([LabelTransactionsBlock.tsx:215](cfos-office/src/components/chat/LabelTransactionsBlock.tsx:215) and [LabelTransactionsBlock.tsx:322-334](cfos-office/src/components/chat/LabelTransactionsBlock.tsx:322))
- Completed read-only state preserves the submitted labels (idempotent if the user reloads)
- Visual contract: `docs/design/prototypes/label-transactions-prototype.jsx` (557 lines of design source)

### What a user sees

A new in-chat capability. When the LLM hits a multi-intent category (e.g. eating-out has both takeaway and dinners-out and they're going to different quadrants), instead of speculating it can ask the user to label 3-6 sample transactions inline. This both **resolves ambiguity** and **demonstrates the system getting smarter** — each label updates `value_category_rules` via the learning engine, and the LLM can later quote "your Tuesday Pret is Foundation" with confidence.

### Risk / fallback

The block is purely chat-surface and cohort-gated via the LLM (v1 path doesn't know about the `label_transactions` tool). If the corrections-signal endpoint fails, the user sees the labelling complete locally but the DB doesn't update — there's no surfaced retry UI. Live test before rollout: induce a 500 on `/api/corrections/signal` and watch the UX.

## 6. Cross-cutting: output-discipline validators + telemetry

### Validators — net new on v2

[cfos-office/src/lib/ai/insight-validator.ts](cfos-office/src/lib/ai/insight-validator.ts) gains four post-LLM checks that run synchronously inside `onFinish` in [app/api/chat/route.ts](cfos-office/src/app/api/chat/route.ts) when (and only when) the conversation is `type = 'first_insight'` AND the v2 flag is on:

- **`validateCitations`** — every number ≥ 10 and every merchant in the prose must trace back to a tool result (citation allowlist built from the run's `toolResults` + the user brief). ±1 unit tolerance to absorb legitimate rounding ([insight-validator.ts:67-90](cfos-office/src/lib/ai/insight-validator.ts:67)).
- **`validateProjections`** — any phrasing like "€X saved per year" or "€X/month" must be backed by a `propose_experiment` tool call whose `monthly_impact.amount` / `annualised_impact.amount` matches the cited figure.
- **`validateVoice`** — flags banned reflexive-CFO phrases ("I noticed", "advice", "let me know", "worth holding in mind", etc.).
- **`validateChips`** — chips must reference a noun from the narrative, must not be generic ("Tell me more"), must not be navigational. Bad chips are stripped via `removeInvalidChips`.

If any of citations / projections / voice fail, `appendCorrection` adds an italic server correction to the message body ([chat/route.ts:776-794](cfos-office/src/app/api/chat/route.ts:776)). The user sees this corrected text directly. Telemetry: a `first_insight_validator_fired` row lands in `user_events` with the full check payload. Bad chips fire a separate `first_insight_chips_stripped` event for cleaner per-validator analytics ([chat/route.ts:801-820](cfos-office/src/app/api/chat/route.ts:801)).

### Telemetry surfaces

- **`proposed_experiments` table** (migration 051) — RLS-pinned. Every `propose_experiment` tool call writes a row regardless of whether the user accepts. Captures the experiment type (`reduce_merchant` / `pause_recurring` / `consolidate_category` / `cap_category` / `redirect_to_goal`), monthly/annualised impact, and the LLM's hypothesis text. The accept-flow UI is explicitly deferred.
- **`first_insight_validator_fired`** event — payload includes `citationCheck` / `projectionCheck` / `voiceCheck` so we can see which validator caught what.
- **`first_insight_chips_stripped`** event — payload includes `invalid_chips` and per-chip `reasons`.

### Risk / fallback

The validator block runs server-side and is `void`-fired so a Supabase insert failure doesn't block the user response. Citation rejections are forgiving (±1 unit tolerance) to avoid false positives on legitimate rounding. The bigger risk is the **validator-fired rate** in production: if > 5% of v2 first-insight conversations trigger a server correction, either the prompt isn't tight enough or the tools aren't returning what the LLM expects. Per the rollout doc, monitor for 5 days post-cohort-flip.

## 9. Verdicts and risk callouts

### What's safe to ship

- All five surface changes are cohort-gated. v1 codepaths are intact. Rollback is `UPDATE user_profiles SET beta_cohort = NULL WHERE id = '<user>'` per user, or unsetting `CHAT_INTELLIGENCE_V2_FORCE` in env.
- Migrations 050 (cleanup) + 051 (telemetry table) are RLS-clean per SESSION-LOG; 050 has been applied to staging only.
- The Value Map flow, archetype reveal, and chat surface are visually unchanged for non-cohort users.
- `unsure` ↔ `no_idea` is bidirectionally tolerant in the DB enum; partial deploys are safe.
- 459 tests passing; `npx tsc --noEmit` clean; `npm run build` succeeds (per SESSION-LOG verdicts).

### What to watch in production

1. **v2 body length.** The live judge result shows the prompt's 100-180 word cap doesn't bind the LLM — User Lew 1's response was 225 words. If the average v2 first-insight response runs >200 words, the tight CFO register erodes. **Mitigation:** add a length check to the validator block; or tighten the prompt's section 6 voice rules.
2. **Validator-fired rate.** Target < 5% of v2 first-insight conversations per the rollout doc. If it's higher, the LLM isn't trusting / understanding tool outputs and the prompt needs adjustment. **Mitigation:** monitor `user_events.event_type = 'first_insight_validator_fired'` daily for 5 days post-flip.
3. **Persona runner.** The runner is currently broken (8/8 failures on staging — Playwright sign-in timeout + user-deletion errors). **Mitigation:** fix the runner before relying on it for evaluation. The deny rule on `cfos-office/tests/**` means this needs a session outside the current deny config.
4. **Multi-intent threshold computation.** The `MultiIntentGapCard.after_labelling` state is wired in the UI but stays in `initial` because the server-side "3+ merchants covering 70%+" threshold isn't computed yet. Cosmetic — the page works — but the "learning is visible" promise of the surface is half-delivered until this lands.
5. **Coverage capture flow.** `CoverageGapCard` opens `/chat?intent=...&category=...` but the chat-side handler for capturing a user's value classification mid-conversation is deferred. Clicking the CTA opens chat with the right context but the system prompt doesn't yet know what to do with it. **Mitigation:** flag for the next session; alternatively wire the chat-side handler before the cohort flip.

### Honest finding from the live run

Neither v1 nor v2 passed the judge's strict gate for User Lew 1. v1 failed because of a structural limitation the rebuild is meant to fix (no merchant citation); v2 failed because of a quality knob that's straightforward to tune (length). The architecture delivers — the tuning isn't done yet.
